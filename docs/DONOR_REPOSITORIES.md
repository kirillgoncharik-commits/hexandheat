## Mandatory controls before any adoption

1. Pin commit/package version plus lockfile integrity; never consume a donor branch or `latest` in CI.
2. Preserve license/notice files and build an SBOM for the selected dependency closure. A package manifest assertion without the license text is not sufficient evidence for commercial release.
3. Treat Math SDK books/events/config as authoritative. Client configuration is generated or checked against the approved math manifest; it is never an independent RTP source.
4. Run software-composition analysis after lockfile resolution. The audited Web SDK directly pins Lodash 4.17.16, which is inside current affected ranges for [GHSA-f23m-r3pf-42rh](https://github.com/lodash/lodash/security/advisories/GHSA-f23m-r3pf-42rh) and [GHSA-r5fr-rjxr-66jc](https://github.com/lodash/lodash/security/advisories/GHSA-r5fr-rjxr-66jc); upgrade and regression-test before use.
5. Do not import donor media. Create original assets with provenance; treat Spine runtimes and any other optional peer as separately licensed.
6. Keep local QA tools out of the shipping bundle and production network path. Cloud uploads, local certificate authorities and credentials require Security Reviewer approval.

## Decision effect on the pilot

The minimal donor set is: Math SDK (authoritative math generation), an adapted and stripped Web SDK scatter application (frontend/RGS/replay), and a local checksum-pinned Stake Dev Tool build for QA. PixiJS skills and Tone.js are POC inputs, not platform authority. Every other donor remains out of the runtime dependency graph.
